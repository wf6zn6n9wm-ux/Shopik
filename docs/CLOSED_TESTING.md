# Закрытое тестирование Nova — чек-лист готовности

Статус на момент составления: **MVP-ядро собрано и зелёное в CI** (OTP → создание
workspace → онбординг → календарь День/Неделя/Месяц → карточка клиента →
Drag&Drop → Push-каркас → онлайн-запись), плюс пройдена дизайн-полировка.
Дальше — **заморозка новых фич** и выход на закрытый трек: TestFlight (iOS) и
Google Play Closed Testing (Android), 50–100 тестеров из разных вертикалей.

Документ — единый источник правды для перехода «код готов → у тестеров в руках».
Разделён на: что уже готово, что **блокирует** запуск, что желательно, план
когорт, сбор обратной связи, посадка фича-флагов и политика заморозки.

---

## 0. Go / No-Go — ворота запуска

Запускаем закрытый трек, только когда **все** пункты ниже — «да»:

- [ ] CI (analyze + test + format) зелёный на релизном коммите.
- [ ] Android AAB и iOS IPA собираются с подписью (не no-codesign).
- [ ] Сборка ставится на чистое устройство и проходит smoke-путь:
      вход → создать workspace → выбрать индустрию → создать услугу/клиента →
      записать → открыть карточку клиента → переключить режимы календаря.
- [ ] Видимость крашей включена (Crashlytics **или** Sentry) — иначе фидбэк слепой.
- [ ] Базовая аналитика доходит до дашборда (хотя бы `sign_up`,
      `workspace_created`, `appointment_created`).
- [ ] Канал сбора обратной связи готов и вписан в приложение/письмо тестеру.
- [ ] Посадка фича-флагов для закрытого трека зафиксирована (раздел 6).
- [ ] Политика приватности опубликована по URL (обязательна для обоих сторов).

## 1. Уже готово (зелёное)

- **Продукт-ядро:** OTP-вход, создание workspace, онбординг по индустриям
  (16 шаблонов, Time-to-First-Value ~30 c), календарь Д/Н/М, карточка клиента,
  Drag&Drop, каркас напоминаний, экран онлайн-записи.
- **Архитектура:** ports & adapters, feature-first, Riverpod, Drift (offline-first),
  go_router, мульти-тенант (`businessId`), мульти-валюта/таймзона, i18n-каркас,
  единый каталог аналитических событий, система фича-флагов.
- **CI:** `ci.yml` — analyze/test/самоисцеляющийся format.
- **Сборки:** `build.yml` — Android APK/AAB, iOS (no-codesign) через
  `flutter create` материализацию платформ.
- **Fastlane:** iOS `beta` (TestFlight) и Android лейны заведены — ждут секретов.

## 2. Блокеры запуска (обязательно до тестеров)

### 2.1 Подписание и материализация платформ
Сейчас платформенные папки (`android/`, `ios/`) в репозитории **не хранятся** —
CI создаёт их `flutter create`. Для подписанной сборки это нужно закрепить:

- [ ] Зафиксировать **bundle id / applicationId** (сейчас в CI `com.nova.app` —
      подтвердить или заменить на боевой; он неизменен после первой публикации).
- [ ] iOS: Apple Developer аккаунт, App ID, provisioning через **fastlane match**;
      секреты `MATCH_GIT_URL`, `MATCH_PASSWORD`, `APP_STORE_CONNECT_API_KEY`.
- [ ] Android: keystore + `google-play` service-account JSON; секреты в CI.
- [ ] Решить судьбу платформенных папок: либо коммитить их (стабильнее подпись),
      либо материализовать в CI и накатывать иконки/сплэш/Info.plist патчем.
      → **Рекомендация:** закоммитить `android/` и `ios/` для контроля подписи,
      иконок, разрешений и `Info.plist`/`AndroidManifest`.
- [ ] Иконка приложения и splash (сейчас дефолтные от `flutter create`).
- [ ] Разрешения: iOS `Info.plist` (уведомления, контакты — под будущий импорт),
      Android manifest (POST_NOTIFICATIONS на 13+).

### 2.2 Видимость проблем (иначе тест бессмыслен)
- [ ] Подключить **Crashlytics или Sentry** (адаптер уже предусмотрен портами) —
      без стектрейсов краши от тестеров невозможно разбирать.
- [ ] Аналитический адаптер: заменить локальную заглушку на реальный сток
      (Firebase Analytics или PostHog). Каталог событий уже единый — нужен только
      адаптер `AnalyticsService`.

### 2.3 Юридический минимум сторов
- [ ] Политика приватности (URL) — обязательна для обоих.
- [ ] Google Play Data Safety форма; Apple Privacy Nutrition Labels.
- [ ] Возрастной рейтинг, категория, контакты поддержки.

## 3. Желательно (не блокирует, но повышает ценность теста)

Заглушки-порты позволяют выпустить закрытый трек **без** этих интеграций —
но тогда соответствующие фича-флаги держим **выключенными**, чтобы не показывать
тестерам пустышку:

- [ ] **Push (FCM)** — реальная доставка напоминаний. Пока `NoopNotificationScheduler`.
      Флаг `push` держать **off**, пока адаптер не подключён.
- [ ] **Подписки (RevenueCat/Stripe)** — сейчас `BillingService`/`Entitlements`
      заглушки. Для закрытого теста можно раздать всем полный доступ (энтайтлмент
      «всё включено») и проверять ценность, а не оплату. Флаг `finances` — off.
- [ ] **Remote Config** — сейчас `LocalRemoteConfigService`. Для реального
      управления флагами без релиза нужен серверный сток (Firebase Remote Config).
      На время закрытого теста локальных дефолтов достаточно.
- [ ] **Онлайн-запись (гостевая web-страница)** — экран бизнес-стороны готов,
      но публичная страница записи для клиентов — отдельная поверхность (v1).
      Флаг `onlineBooking` можно оставить on (шаринг ссылки), но помечать web как
      «скоро».

## 4. План когорт (50–100 тестеров, разные вертикали)

Цель — проверить универсальность на **непохожих** бизнесах, а не только на бьюти.
Набирать по 4–8 человек на вертикаль из разных групп:

- Услуги для людей: барбер/парикмахер, ногти/брови, массаж/СПА, тренер.
- Здоровье: стоматология, ветклиника, небольшая клиника.
- Обучение/творчество: репетитор, фотограф, кондитер.
- Авто/дом: автосервис, автомойка, клининг, мастер на час.
- B2B-услуги: юрист/консультант.

Для каждой когорты фиксируем: подошёл ли шаблон индустрии, хватило ли ресурсной
модели (кресло/кабинет/машина/студия/печь), понятен ли календарь, за сколько
дошли до первой записи (TTFV).

## 5. Сбор обратной связи и метрики

- [ ] Внутриприложенческая кнопка «Написать нам» (email/Telegram) — минимально.
- [ ] Короткая форма (5–7 вопросов) после 3-го дня использования.
- [ ] Северная звезда и воронка активации по событиям каталога:
      `sign_up → workspace_created → industry_selected → service_created →
      client_created → appointment_created`. Смотрим drop-off по шагам.
- [ ] Ретеншн D1/D7; для закрытого теста важнее — доля дошедших до первой записи.
- [ ] Еженедельный разбор: топ-краши, топ-жалобы, топ-«где застряли».

## 7. Политика заморозки

С момента выхода на закрытый трек:

- **Стоп новым фичам.** Только: баг-фиксы, краш-фиксы, тексты/переводы,
  правки онбординга по фидбэку, донастройка шаблонов индустрий.
- Любая новая фича — за фича-флагом **off**, чтобы не дестабилизировать когорту.
- Релизы в закрытый трек — по тегу `vX.Y.Z` (уже триггерит `build.yml`).
- Ветку разработки держим зелёной; мержим только прошедшее CI.

## 8. Ближайшие шаги (предлагаемый порядок)

1. Закоммитить `android/`/`ios/`, иконку, splash, разрешения, bundle id.
2. Подключить Crashlytics/Sentry + реальный аналитический адаптер.
3. Завести секреты подписи (match / keystore / service-account) в CI.
4. Собрать подписанные AAB/IPA, прогнать smoke-путь на устройствах.
5. Опубликовать политику приватности, заполнить Data Safety / Privacy Labels.
6. Залить первые сборки в TestFlight и Play Closed, пригласить пилотную когорту.
7. Включить сбор фидбэка, начать еженедельный разбор.

> Пункты 2–3 требуют аккаунтов и секретов (Apple Developer, Google Play,
> Firebase/Sentry/RevenueCat) — это решения и доступы на стороне владельца
> продукта. Код и порты под них уже готовы; нужна только «проводка» адаптеров
> и ключи.
